# خروج از MVP — برنامهٔ اجرا

**وضعیت:** کارفرماها و مدارس موافقت کردند از همهٔ امکانات واقعی استفاده کنند.  
**مقاطع:** دورهٔ اول ابتدایی، دورهٔ دوم ابتدایی، دورهٔ اول متوسطه، دورهٔ دوم متوسطه.  
**مرجع قبلی:** [`POST_INTRO_PLAN.md`](POST_INTRO_PLAN.md)  
**تاریخ:** ۱۴۰۵/۰۶/۲۸

---

## تصمیم

**بله — از حالت MVP خارج می‌شویم.** پایلوت برای اعتماد بود؛ اعتماد گرفته شده. دیگر نقش و صفحه را به‌خاطر «پایلوت» نیمه‌کاره نگه نمی‌داریم.

**نه — همه را یک‌جا روشن نمی‌کنیم.** خروج از MVP یعنی بک‌اند واقعی، دادهٔ واقعی، و مقطع درست؛ نه روشن‌کردن stubهای مالی/منشی/کتابدار در یک اسپرینت. هر قابلیت وقتی از «به‌زودی» درمی‌آید که ذخیره و RLS و خالی‌بودن صادقانه داشته باشد.

قوانین ثابت:

- مخفی‌سازی منو ممنوع؛ تا بک‌اند آماده شود برچسب «به‌زودی» می‌ماند.
- دادهٔ جعلی نشان داده نمی‌شود.
- Next.js 15/16 و mass-upgrade و صف AI و هدف ۱۰k در این موج نیست.

## P4 و P5 از همین گفتگو — چه مانده؟

| کد | معنی در گفتگو | وضعیت | کار باقی |
|----|----------------|--------|----------|
| **P4-ظرفیت** | سخت‌سازی ~۳۰۰۰ دانش‌آموز / ~۵۰۰ همزمان | ✅ انجام شد | فقط مانیتور SLO |
| **P4-نقش‌ها** | stub معاونت‌ها (~۳۰+) | ✅ C1–C6 MVP | عمق بیشتر + پیامک مالی بعداً |
| **P5** | Dependabot قرمز | ⏳ برش باریک ✅ | Next روی `14.2.35` پین شد. major به ۱۵/۱۶ نه. بقیهٔ Critical/High با بازبینی انسانی |

این سند **P4-نقش‌ها + عمق محصول + مقطع‌ها** را جلو می‌برد. **P5** موازی و باریک است، نه پیش‌نیاز مهر.

## ترتیب اجرا (قفل)

```
A تثبیت اول مهر  →  B مقطع به‌عنوان محصول  →  C نقش‌های عملیاتی باقی  →  D مسیر معلم/والد/دانش‌آموز  →  E P5 باریک
```

فاز B می‌تواند با انتهای A هم‌پوشانی داشته باشد. فاز E از فردا قابل شروع است و به C وابسته نیست. فاز ظرفیت ۱۰k شروع نشود مگر رشد واقعی از ۳۰۰۰ گذشت.

## فاز A — تثبیت نقش‌های اول مهر (هفتهٔ ۱)

هدف: همان شش نقش از «MVP نازک» به «قابل استفادهٔ روزانه» برسند.

نقش‌ها: مدیر، مشاور، بهداشت، انضباطی، آموزشی، پرورشی.

| # | قدم | معیار اتمام |
|---|-----|-------------|
| A1 | ساخت کاربر واقعی هر نقش (ادمین یا bulk import). «معاون پرورشی» → `nurturing_vp` نه انضباطی | ورود هر نقش به خانهٔ درست (`lib/auth/roles.ts`) |
| A2 | مدیر: شمارش مدرسه + لینک به حضور/رفتار/بهداشت بدون عدد ساختگی | خالی بودن مدرسه صادقانه است |
| A3 | مشاور: پروندهٔ جدید / فهرست / جزئیات / آمار روی `counseling_records` | بدون علی رضایی |
| A4 | بهداشت: آمار + فهرست پرونده روی API سلامت | |
| A5 | انضباطی: حضور مدرسه + گزارش رفتار معلمان | |
| A6 | آموزشی: برنامه و قفل برنامه؛ فعالیت پرورشی اینجا ساخته نمی‌شود | `canLockTimetable('nurturing_vp') === false` |
| A7 | پرورشی: ثبت و فهرست `nurturing_activities` | RLS مدرسه؛ PATCH/DELETE با migration `169` |
| A8 | تست دستی یک مدرسه روی Production بعد از دیپلوی `168`/`169` | چک‌لیست نقش‌ها در [`PILOT_ALLOWED_MENU.md`](PILOT_ALLOWED_MENU.md) |

**S1 کدی (عمق روزانه):** بهداشت create/edit، انضباطی حضور+رفتار write، ویرایش مشاور، پرورشی update/delete — انجام شد در کد؛ ساخت کاربر واقعی همچنان Ops است.

خروجی فاز A: مدرسه می‌تواند مهر را با همین شش نقش شروع کند.

## فاز B — مقطع به‌عنوان محصول (هفتهٔ ۱–۲)

هدف: چهار مقطع اول‌کلاس باشند، نه فقط فیلتر پایه.

وضعیت فعلی کد:

- دانش‌آموز: `education_stage` با `elementary | middle_school | high_school | …` (پایه‌های ۱–۶ یکجا «ابتدایی»).
- مدرسه: `schools.education_stage` همین مجموعه.
- محدودیت مسیر: کنکور / قطب‌نما / راهنمای AI فقط متوسطه ([`lib/security/grade-restricted-routes.ts`](../lib/security/grade-restricted-routes.ts)).

شکاف قبلی: **دورهٔ اول و دوم ابتدایی از هم جدا نبودند.**

**S2 در کد:** هلپر [`lib/education/cycle.ts`](../lib/education/cycle.ts) چرخه را از پایه می‌سازد (۱–۳ / ۴–۶ / ۷–۹ / ۱۰–۱۲) بدون شکستن enum DB. منو با `resolveNavGroups(role, { grade })` فیلتر می‌شود؛ middleware مسیرهای کنکور/AI را برای ابتدایی با پیام فارسی مسدود می‌کند.

| # | قدم | وضعیت |
|---|-----|--------|
| B1 | هلپر چرخه از grade | ✅ |
| B2 | enum مدرسه/دانش‌آموز دست‌نخورده | ✅ |
| B3 | منو + middleware بر اساس چرخه | ✅ |
| B4 | پرامپت AI بر اساس پایه | ⏳ موج بعدی |
| B5 | برنامهٔ کلاسی مدرسه‌محور | ✅ از قبل |

خروجی فاز B: یک مدرسهٔ ابتدایی و یک مدرسهٔ متوسطه رفتار متفاوت و درست دارند.

## فاز C — نقش‌های عملیاتی باقی (هفتهٔ ۲–۴) = باقی P4-نقش‌ها

ترتیب بر اساس اول مهر، نه کامل‌بودن نقشهٔ قدیمی. هر نقش یک اسپرینت کوچک: جدول + RLS + API + صفحه + بدون دادهٔ جعلی.

| ترتیب | نقش | وضعیت | حداقل محصول واقعی |
|--------|-----|--------|-------------------|
| C1 | منشی | ✅ | جلسات + نامهٔ داخلی (`school_meetings` / `correspondence_items`) |
| C2 | معاون مالی + شهریه ادمین + مالی والد | ✅ | پرداخت/بدهی/درآمد واقعی؛ پیامک همچنان «به‌زودی» |
| C3 | معاون ارزشیابی | ✅ | ارزیابی معلم + آمار |
| C4 | کتابدار | ✅ | امانت + جستجو روی موجودی |
| C5 | معلم هنر / معلم ورزش | ✅ | گزارش هنر/ورزش روی دانش‌آموز مجاز |
| C6 | حراست + تأسیسات | ✅ | ورود/خروج و درخواست تعمیر؛ برنامهٔ تأسیسات «به‌زودی» |

Migration: `170_remaining_staff_role_mvps.sql` (در ریپو؛ روی Production با MCP/SQL Editor اعمال شود اگر `db push` به خاطر DNS/IPv6 گیر کرد).

پیامک مالی بدون هماهنگی کارفرما روشن نشود.

خروجی فاز C: نقش‌های پشتیبانی خانهٔ واقعی دارند؛ فقط موارد بدون بک‌اند «به‌زودی» می‌مانند.

## فاز D — بستن «به‌زودی»های پرمصرف (هفتهٔ ۳–۵)

فقط آیتم‌هایی که مدرسهٔ واقعی در مهر/آبان می‌خواهد.

| مخاطب | وضعیت | کار |
|--------|--------|-----|
| معلم | ✅ | ارزیابی مهارت پایه + اعطای نشان (API واقعی / XP موجود) |
| مشاور | ⏳ | بینش خانواده هنوز «به‌زودی» |
| دانش‌آموز | ⏳ | راهنمای AI، زمین بازی، کنکور/قطب‌نما — محدود به مقطع؛ بک‌اند بعدی |
| ادمین | ⏳ جزئی | شهریه فعال؛ مصرف/مدل/اعتبار AI و قابلیت‌ها هنوز «به‌زودی» |

خروجی فاز D (این موج): منوی روزمرهٔ معلم برای مهارت پایه و نشان دیگر تئاتری نیست؛ ابزارهای AI دانش‌آموز عمداً «به‌زودی» ماندند.

## تعریف مدرسهٔ آماده (DoD محصول، نه پایلوت)

مدرسه وقتی «از MVP خارج شده» حساب می‌شود که:

1. مقطع‌اش معلوم است و منو/AI همان مقطع را نشان می‌دهد.
2. نقش‌های حاضر در آن مدرسه خانهٔ واقعی دارند (نه RoleInactive).
3. والد/معلم به عدد ساختگی برخورد نمی‌کنند.
4. ورود گروهی نقش پرورشی را اشتباه به انضباطی نمی‌برد.
5. خطا و حالت خالی فارسی و صادقانه است.
